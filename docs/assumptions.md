## Ambiguities and design decisions

D-01 to D-07 were identified in Stage 00 and resolved in Stage 02. D-08 to D-17 were found and decided in Stage 02, D-18 to D-22 in Stage 03, D-23 to D-29 in Stage 04, D-30 to D-36 in Stage 05, D-37 to D-42 in Stage 06, D-43 to D-49 in Stage 07, D-50 to D-53 in Stage 08, D-54 to D-63 in Stage 09, and D-64 to D-66 in Stage 10.

| ID | PDF p. | Ambiguity | Decision |
|---|---|---|---|
| D-01 | 6-7 | Which report is meant by "TB", "same as Odoo behavior" and "Odoo's dynamic reports" | The native Enterprise Trial Balance (`account_reports.trial_balance_report`) in the `account_reports` UI. Its conventions are adopted where the assessment expects the standard report (A-14, A-15). Its UI and exporters host our report (A-13). Confirmation: Q-03 |
| D-02 | 7 | Journals and Analytic Accounts are Many2one, but their help texts say "specific journals" / "specific analytic accounts" | Keep Many2one (one journal, one analytic account, or empty for all). Use the PDF help texts verbatim. The native multi-select filters are disabled in our preview so the contract cannot be widened |
| D-03 | 7 | The wizard field list has no date or company fields, yet the PDF header needs "the selected date range" | Add Date From, Date To (required, inclusive, default the current month) and one Company (required, from the user's active authorized companies). The engine scope is exactly that company; branches are separate companies (D-16) |
| D-04 | 7 | Meaning of Debit/Credit for the Initial and Ending columns | Native convention: Initial and End Debit/Credit show the net side of the signed balance; Movement Debit/Credit are gross period totals; each group also shows its signed Balance (debit positive). Group rows sum their children's displayed debit and credit separately, as the native hierarchy does (probe R8). Totals sum leaf rows |
| D-05 | 6 | Project-size buckets "<5, 5-10, 11-25, 25+" leave a gap for fractional values and overlap at 25 | Buckets [0, 5), [5, 11), [11, 25), [25, inf) labeled "Below 5", "5 to below 11", "11 to below 25", "25 and above", plus "Unknown" when `average_project_size` is not known. 25 belongs only to the last bucket |
| D-06 | 5 | Top/Bottom 5 ranking versus the shared filters, and ties | Rank after all three shared filters. Count active partners in active countries. Only countries with at least one matching partner take part. Ties are broken by count, then country name, then id. With fewer than 5 countries, all are shown; with fewer than 10, the two cohorts may overlap, and the dashboard says so. An empty result shows a clear message |
| D-07 | 6-7 | How the Analytic Account filter treats journal items whose distribution spans several accounts | Native whole-item inclusion: an item counts at its full amount, once, when any key of its distribution (composite keys included) contains the selected account. Without a filter each item counts once. Proportional allocation remains a documented alternative, not the default (Q-03) |
| D-08 | 3 | "A message should be posted in the internal chatter of a designated user" | An internal note on the failed run's chatter (`sync.run`, a `mail.thread`), addressed to the configured user through `partner_ids`. Odoo delivers it according to the user's notification preference (Inbox or email). In a fresh database of this build, `admin` uses email, so the demo steps include switching to "Handle in Odoo". Alternatives considered: a note on the user's contact record, or an OdooBot direct chat. The run's chatter keeps the report next to its evidence |
| D-09 | 4 | `current_status` is "Selection (e.g., 'gold', 'silver', 'ready')"; the site may show another label | Ordering ready < silver < gold. An unknown label is a parse error for that partner: the unit fails, the error is logged and retried, and nothing is written. It is never coerced to Ready, and no fourth change type is invented |
| D-10 | 4 | A removed reference that reappears | Each reference record is one listing interval. A reappearing reference creates a new active record, so earlier `added_on`/`removed_on` dates are kept. At most one active record exists per (partner, reference key) |
| D-11 | 7 | Date scope of the Show Amount Currency column | The column shows the period movement (Date From to Date To, inclusive) in each row's transaction currency. Rows are grouped by account, then currency. Group and total rows leave it empty, and a separate per-currency totals section is added. The help text is the PDF's text plus one sentence stating this scope |
| D-12 | 7 | Which accounts appear when Skip Zero Balance is off | Every non-deprecated account of the company that matches the account filter, even without journal items, plus any account with amounts. With the option on, a row is hidden only if its opening balance, movement debit and movement credit are all zero (currency-aware). Equal debit and credit movement stays visible |
| D-13 | 6 | "Hierarchy Only Parents" and "Account Level Up To 1-5" | Only Parents is available only with Hierarchy and Subtotals. It shows group rows of level N or less, plus "(No Group)", and no account rows. Each shown group aggregates all its descendants. Level = depth in the `account.group` tree (1 = top group). Invalid combinations are rejected server-side |
| D-14 | 5 | "Year First Seen" | The year of `first_seen_on`, the date our scraper first observed the partner, not when the partner joined Odoo. On a new installation all partners share the installation year, so the demo data spreads several years |
| D-15 | 6-7 | Account-prefix filter versus the fiscal-year carry-forward | As in the native report: the carry-forward sums all income and expense accounts within the other filters, and is shown on the "Current Year Earnings" row only if that row matches the account filter |
| D-16 | 7 | Branches of the selected company | The report scope is exactly the selected company. A branch is reported by selecting it. The native report would include accessible branches; parity tests use companies without branches |
| D-17 | 4-5 | A partner absent from its country's listing, or listed under another country | Absence from a validated complete snapshot of its last country archives the partner (`active = False`), unless it is seen in another country, which updates `country_id`. Identity is the site's partner id, never the name or the country |
| D-18 | 4 | Who may change scraped data, audit events and sync checkpoints (Stage 03) | Nobody, through access rules: every Partner Monitor ACL is read-only, and only the sync engine (superuser) writes. Managers get four actions instead (Sync Now, Retry, Mark for Re-scrape on countries and partners), which check the manager group and then write with a narrow `sudo()`. Status history rows cannot be edited at all. Settings stay with system administrators (A-22) |
| D-19 | 3 | Default failure recipient, "e.g. the administrator who installed the module" (Stage 03) | `base.user_admin`, set by a `noupdate` data record. Odoo runs install hooks as the superuser, so the user who clicked Install is not known to the module. Changing the default is one setting. Replaces the post-init-hook plan of Stage 02 (P-07.4) |
| D-20 | - | How demo data is kept apart from scraped data (Stage 03) | Demo records have `is_demo = True` and names starting with "Demo". They use reserved website ids: negative partner ids and country ids starting with "demo-". Database checks keep these namespaces apart, so a real scrape can never update or collide with a demo record. Demo partners have no `partner_url` |
| D-21 | 4 | An observation older than the partner's last observation (Stage 03) | Ignored, so a late replay of an earlier run cannot record a false demotion or promotion. Observations of the same day are applied |
| D-22 | 4-5 | Unknown versus zero for `total_references_count` (Stage 03) | Like the three metrics in architecture 5.2, it has a `_known` flag: reference validation needs a known expected count. A database check ensures an unknown measurement carries no number |
| D-23 | 5 | Identity of a reference client (Stage 04) | The id in its `/customers/<slug>-<id>` link, else the same id in its avatar image URL, else (fallback) its normalized name. Two clients with the same name but different ids stay two references; the name is used only when the page shows no id |
| D-24 | 4 | An unknown status label on a listing card (Stage 04; refines D-09) | That card is skipped and reported as invalid; the other cards are recorded. The country snapshot is then incomplete, so nothing is archived and the country is flagged. On a partner's own page, an unknown status fails the whole page and nothing is written |
| D-25 | 3, 5 | Crawling rules of the site (Stage 04) | Follow robots.txt as read on 2026-11-08: never request URLs whose query has `country_id`, `grade_id`, `page` and similar keys, or `*/page/*/*` paths. | D-26 | 5 | Language of the parsed pages (Stage 04) | The parsers read English labels ("Average Project", "References", the no-partners notice), so pages must be requested in English. This is part of the deferred page-download module |
| D-27 | 5 | When an empty country is confirmed (Stage 04) | The site's no-partners notice alone is not enough. It counts as a valid empty result only when a complete country list read in the same run does not list the country, or lists it with 0 partners. Otherwise the result is incomplete and existing records are kept |
| D-28 | 5 | When a country snapshot is complete (Stage 04) | Every page from 1 to the last was read in order; every card was in scope and readable; nothing was listed twice; and the number of distinct partners equals the page's own "All Categories" count. Reading only the last page, or pages with a gap, is never complete |
| D-29 | 4 | Which page decides that a metric is unknown (Stage 04) | The listing card, shown for every partner: a value it does not show is stored as unknown. A partner's own page only adds the values it shows. A value the site prints as 0 ("0 users") is a known 0 |
| D-30 | 4 | Which date the sync records (Stage 05; replaces A-20) | The UTC date on which the unit reads the page. Units of one run can run on later days (retries with backoff, a run waiting for its page source), and a page is observed when it is read. D-21 still ignores an older observation |
| D-31 | 4-5 | When a partner's own page is read, and what "changes in retention rate or project size can trigger the flag" means (Stage 05) | Read in the same run for a new partner (first contact, not a mismatch). For a partner read before, a listing card whose hash of retention rate, average and largest project size and reference count differs from the previous card sets `to_reprocess_references`, and the reference-validation job reads the page. Flagged mismatches and pages read more than 7 days ago (at most 200 per call) are read too. The hash compares cards with cards, so reading the page cannot trigger another read ([resilience.md](resilience.md) 9) |
| D-32 | 3, 5 | Retry limits (Stage 05) | A failed unit gets at most 5 tries, 15, 30, 60 and 120 minutes apart (doubling, capped at 24 hours), then stays `failed` and visible. | D-33 | 3 | What the worker does without a page source (Stage 05; the page-download module is deferred) | Nothing is attempted: units stay pending with no try counted. | D-34 | 3 | When a run is done, partial or failed, and how often it notifies (Stage 05) | Done: no unit failed. Failed: no unit succeeded. Partial: both. Cancelled units are ignored. One note per run (`notified_at`), also when a manager's retry ends it again |
| D-35 | 3 | How a worker claims a unit (Stage 05; detail of A-18) | A row lock (`FOR NO KEY UPDATE SKIP LOCKED`) held until the batch's transaction ends, so no lease is needed: a crash releases it.
